# diff/ の作業ルール

`diff/01-xxx-xxx.md` を書くときの規則。

このファイルは監査スキルの雛形である。`<形式化系>`（Lean / Isabelle / Coq など）と
`<形式化ルート>`（`lean/` など）は対象リポジトリに合わせて置換してから使う。
以下では `<形式化系>` を `Lean`、`<形式化ルート>` を `lean/` と書く。

## 1. 章構成

```
[< back](README.md)
# (命題番号): (タイトル)

## 原文

### 命題
(原文中の命題番号)
(命題)

### 証明
(原文記載の証明をそのまま引用)

## Lean

### Lean での命題
(Lean の証明対象の命題。lean 言語ではなく mathjax 数式で書く)

### Lean での証明
(Lean の証明。lean 言語ではなく mathjax 数式で書く)

## 原文通りに書けなかった理由
(原文との差異を分類つきで列挙。§10 参照)

### lean との対応
(上の数式が Lean のどの宣言に当たるかの対応表。ここだけ Lean 識別子を書いてよい)

```

見出しの文言と階層は変えない。

## 2. アウトラインを書かない（最重要）

**求めているのはアウトラインではなく、証明の詳細である。**

Lean の証明を数式に直すとき、「ここはだいたいこういう証明をする」という要約だけを書いて
細部を省略してはいけない。Lean に書いてある細かい式を全部数式にして、
**原文の証明と一行ずつ突き合わせられる**状態にする。

### 悪い例

> 補題 8.4 を使って充足コードの正しさを得る。$\Delta_0$-絶対性から外部でも成立するので、
> 正表示の同値が従う。負表示も同様。

何を何に適用したのか、どの集合を取ったのか、絶対性がどの包含関係から出るのかが書かれていない。

### 良い例

> $a$ の値域を含む推移的集合として $A$ を取る。具体的には $\rho$ を
> $\omega + 1 < \rho < \theta$ かつ $\rho + 1 < \theta$ なる順序数とし $A = L_\rho$ と置く。
> このとき $A$ は推移的で、$\mathrm{ran}(a) \subseteq A$、$A \in L_{\rho+1} \subseteq W$。
> 次に補題 10.5(1) を $W$ の内部で $A$ に適用して $U, T \in W$ で
> $W \models \mathrm{SatCode}(A,U,T)$ なるものを取る。$\mathrm{SatCode}$ は $\Delta_0$ で
> $W$ は推移的だから、$\Delta_0$-絶対性により外部でも $\mathrm{SatCode}(A,U,T)$。
> 補題 8.4 から $\langle e,a\rangle \in T \iff (A,\in) \models \delta[a]$。…

（上の 2 例は別プロジェクトのもので、粒度の見本として置いてある。）

### 分量の非対称は許される

原文の証明が 3 行でも、Lean の証明が 200 行なら **Lean 側は 200 行ぶんの内容を書く**。
「原文が短いから Lean も短く」は誤り。差異を見せるのがこのページの目的なので、
違うところほど詳しく書く。

逆に、原文と Lean が同じ筋で進むところは「原文と同じ」と書いて短くしてよい。
ただしどこまでが同じでどこから違うのかは明記する。

### 読んでいないものを書かない

数式に直す前に、その宣言と証明を**実際に開いて読む**。名前から中身を推測して書かない。
補助補題を引くときも、その補助補題の主張を読んでから書く。読まずに書いた行は、
たいてい原文寄りに歪む（原文どおりに見えてしまう）ので、監査の意味が失われる。

## 3. Lean のコードを書かない（ただし最後の一節は例外）

「Lean での命題」「Lean での証明」は数式で書く。Lean の識別子もファイル名も書かない。
名前が要るときは、原文の記号か、原文に無ければ日本語の名前を使う。

- 悪い: $\mathrm{IsCodeW}\ h\ w\ e$
- 良い: $\mathrm{Form}(e)$、または「整式コード判定」

**例外は「### lean との対応」の節だけ。** ここには識別子とファイル名を書く。
数式だけでは Lean のどこを読めばよいか分からないので、対応表を最後に一つ置く。

### 「lean との対応」の書き方

上の 2 節に出てきた**数式の名前**を左に、対応する Lean の宣言を右に置いた表にする。
出てきた順に並べる。

| 数式 | Lean | ファイル |
|---|---|---|
| $\mathrm{Form}(e)$ | `IsCodeW h w e` | `SetTheory/Code.lean` |
| $\mathrm{Last}(s) = e$ | `IsLastW w s e` | 同上 |
| $\mathrm{Form}$ は $\Delta_0$ | `delta0_isCodeW` | 同上 |
| $\mathrm{Form}(e) \iff \exists\varphi\,(e = \ulcorner\varphi\urcorner)$ | `isCodeW_iff` | 同上 |

- ファイルは `lean/` からの相対パスで書く。
- **行番号は書かない。** すぐ古くなる。
- 証明の途中でしか使わない補題も、証明の記述に名前を出したなら表に載せる。
- 対応物が無い数式は右を「なし」とし、なぜ無いかは「原文通りに書けなかった理由」で述べる。

## 4. 原文はそのまま引用する

「原文記載の証明をそのまま引用」とある通り、要約しない。原文が省略している箇所は
省略されたまま書き、補ったのは Lean 側だと分かるようにする。

数式は原文の記法をそのまま MathJax に直す。記号の置き換えをしない
（$\hat\Sigma_q$ を $\Sigma_q$ にしない、$\prec^*_q$ を $\prec_q$ にしない）。

### 引用に `>` を使わない

markdown の引用記法（行頭の `>`）は使わない。地の文としてそのまま書く。
`## 原文` の節は全体が原文なので、装飾で区別する必要が無い。

- 悪い:

```
> 整式の導出列とは、有限自然数列 $s$ で、その各項が (8.1) の原子式コードであるか、
>
> $$\mathrm{Form}(e) \ :\Longleftrightarrow\ \exists s \in \omega\ (\cdots)$$
>
> と定める。
```

- 良い:

```
整式の導出列とは、有限自然数列 $s$ で、その各項が (8.1) の原子式コードであるか、

$$\mathrm{Form}(e) \ :\Longleftrightarrow\ \exists s \in \omega\ (\cdots)$$

と定める。
```

## 5. 監査の経緯を書かない

読者が知りたいのは **いまの Lean と原文の差異**と、**なぜまだ原文どおりに書けていないか**の
2 つだけである。そこへ至る経緯は書かない。

書かないもの:

- 「監査 U-30 の指摘は 2 段構えだった」「U-48 は解消済み」など監査番号への言及
- 「以前は … だった」「… に直した」「… を新設した」など変更の履歴
- 「解消した部分」という節
- 「着手していない」「差し戻した」「見送った」など作業の進捗

書くもの:

- いまの Lean がどうなっていて、原文とどこが違うか
- その差異が消せない理由（構造的な障害）、または消すのに要る作業の内容と規模

差異が無くなった項目は、単に「原文どおりに書けている」と書く。何がどう直ったかは書かない。

## 6. 対応物が無いときは、無いと書く

原文にあって Lean に無いものは「対応物なし」と明記し、代わりに何があるかを書く。
無いものを「実質的にはこれが対応する」とごまかさない。

## 7. 命題が複数の主張を持つとき

(1)(2)(3) と分かれている命題は、原文・Lean とも項目ごとに分けて書く。
項目ごとに差異の有無や分類が違うことがあるので、まとめない。

## 8. 目次を更新する

ページを追加・改名したら [README.md](README.md) の目次も更新する。

## 9. 公開範囲

このリポジトリの外にあるファイルの名前・内容に言及しない。`tmp/` 以下にも言及しない。
論文は「原文」「論文」とだけ呼ぶ。

## 10. 差異には分類を付ける

`## 原文通りに書けなかった理由` の節には、**原文と Lean の差異をすべて**書く。
「原文どおりに書けなかったもの」だけでなく、**原文の飛躍を埋めたもの**（Lean のほうが
長い）、**原文の一部が要らなかったもの**（Lean のほうが短い）も差異である。

差異ひとつごとに、次の 7 分類のうち**ちょうど 1 つ**を付ける。`X` と `Z` には 🚨、
`Y` には ⚠️、`U` には 🌳 を頭に付ける。`W`、`S`、`R` には何も付けない。

| 分類 | 条件 |
|---|---|
| 🚨**X** | 原文をそのまま形式化すると矛盾する。本質的、または規模が大きい |
| ⚠️**Y** | 原文をそのまま形式化すると矛盾する。誤記の類 |
| 🚨**Z** | 原文に飛躍がある。飛躍が本質的で大きい |
| **W** | 原文に飛躍がある。形式化の範疇に収まる小さいもの |
| **S** | 迂回だが原文の主張との差が小さく、下流の内容を変えない |
| **R** | 原文の証明の一部が無くても証明が通る |
| 🌳**U** | 形式化の都合で原文どおりに書けず迂回している |

### 判定の順序

上から順に見て、最初に当たったところで止める。

1. 原文の言明が**偽**か（そのまま形式化すると矛盾するか）。本質的・大規模なら 🚨**X**、
   誤記の類なら ⚠️**Y**。
2. 言明は真だが**証明に飛躍**があるか。飛躍が本質的で大きいなら 🚨**Z**、
   形式化の範疇の作業で埋まる小さいものなら **W**。
3. 原文の証明の一部が**要らなかった**か。→ **R**
4. **迂回**したか。主張の差が小さく下流が変わらないなら **S**、そうでなければ 🌳**U**。

### よくある誤判定

- **W を U と書く**。原文が飛ばした議論をこちらが埋めたのなら、原因は原文側なので
  **W** である。「Lean では書けなかったので補った」と書いて **U** にしない。
- **R を U と書く**。原文の一歩を使わずに済んだのは迂回ではない。**R** である。
- **S を U と書く**。下流が何も変わらないなら **S**。「変わらない」ことを確かめずに
  **S** と書くのも誤りなので、確かめてから書く。
- **X と Y の取り違え**。直し方が一意で機械的なら **Y**、直すと定理の形や証明の構造が
  変わるなら **X**。

### 書き方

節の中に、差異ひとつを 1 項目とする箇条書きを置く。各項目は分類で始め、次に一行要旨、
その下に本文を書く。

```
## 原文通りに書けなかった理由

- **[W]** 原文の「即座に従う」は Lng に関する強帰納法を隠している

  原文は … と書くだけだが、実際には … の場合分けが要る。Lean では …

- **[🌳U]** 単項成分の分解を原文の順序どおりに書けない

  原文は先に … を取るが、この形式化では … が先に必要で …
```

差異が一つも無いときは、箇条書きを置かず `原文どおりに書けている。` とだけ書く。

指摘に通し番号（`W-1`、`U-3` など）を振るのは [README.md](README.md) の役割である。
このページには番号を書かない（§5）。
