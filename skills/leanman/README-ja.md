# leanman

複数エージェントで Lean 4 の証明を並列に検査するための管理コマンドです。1 つの
コマンドで Lean ファイルを検査し、サンドボックス内でも通るバックエンドを自動で
選び、各ジョブに kill 用の短いハンドルを与えます。

スキル本体は [SKILL.md](SKILL.md)、ツールは [scripts/leanman](scripts/leanman)
です。このファイルは人間向けに、何をするもので、なぜこの形なのかを説明します。

## 解こうとしている問題

複数エージェントが同時に Lean の証明を進めると、性質の違う 4 つの壁に当たります。

1. **`lake build` は並列にできない。** `.lake` に書き込むので、2 本走らせると
   互いを壊します。しかし *検査* は何も書きません。「Lean を並列で走らせるな」で
   一括りにするのではなく、両者を分けて扱う必要があります。
2. **沈黙が曖昧。** `lean` は成功時に何も出力しません。そして途中で打ち切られた
   ツール呼び出しも、やはり何も返しません。「出力なし＝証明できた」と読むエージェ
   ントは、検証していない証明を報告することになります。
3. **速い検査器はサンドボックスから届かない。** `codex:rescue` の shell は
   `socket()` / `connect()` / `bind()` を seccomp で全面禁止されているため、
   kimina-lean-server には何をやっても到達できません。curl も UNIX ドメイン
   ソケットも中継プロセスもすべて不可です。
4. **固まった検査を殺すのが危険。** `pkill -f lean` は、狙ったジョブと一緒に他の
   エージェントの作業も巻き添えにします。

## leanman がやること

- `leanman setup` が唯一の直列ステップです。ライブラリをビルドし、`LEAN_PATH` を
  キャッシュし、対応する kimina サーバを探し、そのプロジェクトを既定として記録
  します。
- `leanman check FILE.lean` が作業エージェント用です。どこからでも、並列に実行
  できます。返るのは **0 green / 1 sorry / 2 error / 124 timeout** — 解釈が要る
  沈黙ではなく、数値です。
- kimina が到達可能で **かつ** そのプロジェクトを提供している場合だけ kimina
  （約 0.2 秒）を選び、それ以外は `lean` 直呼び（約 1.3 秒、ネットワーク不要）に
  落とします。サンドボックス内の作業エージェントは同じコマンドで同じ終了コードを
  得ます。
- `check` は共有ロック、`build` / `setup` は排他ロックを取ります。N 本の検査は
  フルスピードで並走し、書きかけの olean を見ることはありません。
- 全ジョブに **leanman-id** が付きます。`leanman ps` で一覧、
  `leanman kill <id>` でどのディレクトリからでも 1 本だけ確実に殺せます。

## 設計メモ

**なぜ環境変数がレジストリなのか。** `isbman` と同じく、各ジョブに `LEANMAN_*` を
注入し、`/proc/<pid>/environ` を走査して自分のプロセスを見つけます。デーモンも
不要、古くなる PID ファイルもなく、サンドボックス内でも動きます（`/proc` の読み
取りと `kill` は許可されているため）。

**なぜ `~/.cache` ではなく `/tmp` なのか。** codex サンドボックスが書き込みを
許すのはワークスペースと `/tmp` だけです。`~/.cache` に状態を置くと、サンドボッ
クス内の作業エージェントが全滅します。`LEANMAN_HOME` の中身はすべて再生成可能
です。

**なぜ `LEAN_PATH` をキャッシュするのか。** `lake` の起動だけで約 1.2 秒かかり、
小さな証明ファイルの実際の elaboration は約 0.09 秒です。`LEAN_PATH` をキャッシュ
して `lean` を直接呼べば、検査 1 回あたりの時間の大半が消えます。

**なぜ kimina をプロジェクトと照合するのか。** kimina の 1 インスタンスは
`LEAN_SERVER_PROJECT_DIR` 1 つだけを提供します。別プロジェクトの環境に対して検査
すると、自信のある間違った答えが返ります。そのためディレクトリが一致するときだけ
kimina を使い、それ以外は黙って遅く確実な経路を選びます。

## 実測値

pss-proof の Lean プロジェクト（Lean 4.30 + Mathlib）、28 コア / 31 GB での計測。

| | |
|---|---|
| `lake env lean`（lake 経由） | 1.81s |
| `lean`（`LEAN_PATH` キャッシュ済み） | 1.29s |
| kimina（常駐 REPL） | 0.07s |
| ファイルの純粋な elaboration | 0.09s |
| 8 並列検査の合計 | 1.79s |
| 並列 1 本あたりの限界メモリ | 約 330 MB |
| サンドボックス内での kimina 探査失敗 | 3ms |

## isbman との関係

[`isbman`](https://github.com/koteitan/isbman) は Isabelle/HOL 向けの同じ発想の
ツールで、leanman は その id ベースの reaping をそのまま借りています。違いは Lean
由来です。heap の隔離が不要（検査は何も書かないので隔離する store が無く、`gc`
サブコマンドも要らない）で、バックエンドが 1 つではなく 2 つある（常駐 REPL が
存在し、届くことがあるため）点です。
